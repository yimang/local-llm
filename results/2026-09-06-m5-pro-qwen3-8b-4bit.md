# M5 Pro MLX benchmark: Qwen3-8B-4bit

## Summary

This run measured single-stream inference performance for the 4-bit MLX build
of Qwen3-8B on a 16-inch MacBook Pro with an M5 Pro and 64 GB of unified
memory. The benchmark used MLX-LM's native benchmark entry point, a pinned
model revision, one warmup, and five measured trials for each prompt and
generation-length combination.

Median generation throughput was **57.363 to 59.971 tokens/second** and was
repeatable: the coefficient of variation was **0.50% to 1.29%** across the
five configurations. MLX-reported peak memory was **4.923 to 5.217 GB**.

Prompt-processing measurements were much less consistent, with coefficients
of variation from **5.25% to 30.56%**. Treat the generation results as a useful
baseline, but repeat the prompt-processing portion after the computer is fully
charged and has cooled before using it for comparisons.

The complete trial-level record is in
[`2026-09-06-m5-pro-qwen3-8b-4bit.json`](2026-09-06-m5-pro-qwen3-8b-4bit.json).

## Scope

This benchmark answers a narrow question: how quickly can this model perform
prefill and autoregressive generation through MLX-LM with batch size one?

It does not measure:

- model quality or correctness;
- tokenizer or model-loading time;
- time to first token as perceived by an application;
- concurrent-request throughput;
- energy consumed per token; or
- performance through another runtime such as llama.cpp.

The prompts are synthetic token IDs rather than natural-language text. This
makes the compute workload repeatable and avoids prompt-content effects, but it
is not an end-to-end application benchmark.

## Test conditions

The run completed at `2026-09-06T07:46:03Z` (approximately 03:46 EDT). Before
the first measurement:

- the power adapter was connected;
- the macOS power-adapter mode was changed from Automatic to High Power;
- the CPU was approximately 89.1% idle;
- load average was 3.20, 2.86, and 2.29; and
- the system reported zero swap-ins and zero swap-outs at preflight.

No deliberate workload was run alongside the benchmark. Direct temperature,
fan, package-power, and energy telemetry was not collected because it was not
available through the unprivileged macOS interfaces used for this run.

At postflight, the system reported 124 swapout pages, approximately 1.94 MiB
with 16 KiB pages. That amount is immaterial for a roughly 5 GB model workload.

The battery was actively charging from a low state throughout the run. Charging
can add heat and consume part of the system power budget, so it is a known
confounding variable. In addition, the configurations were run in a fixed order,
meaning prompt length and elapsed thermal state cannot be separated in this
dataset.

## Methodology

### Environment setup

From the repository root, reproduce the locked Python environment with:

```bash
uv python install
uv sync --locked

uv run --locked python --version
uv run --locked python -c \
  'import mlx, mlx_lm; print("mlx", mlx.__version__); print("mlx-lm", mlx_lm.__version__)'
```

Run the benchmark from an interactive macOS session with access to the Metal
GPU. A headless or sandboxed process may fail with `No Metal device available`.

### Model acquisition

Resolve the exact Hugging Face revision into the local cache:

```bash
MODEL_DIR=$(uv run --locked python -c '
from huggingface_hub import snapshot_download

print(snapshot_download(
    repo_id="mlx-community/Qwen3-8B-4bit",
    revision="545dc4251c05440727734bcd94334791f6ab0192",
))
')

test -d "$MODEL_DIR"
```

The initial download requires network access and roughly 4.7 GB of available
disk space. Subsequent runs reuse the Hugging Face cache.

### Power and preflight preparation

1. Connect the Apple power adapter.
2. Close or pause other compute-heavy applications.
3. In **System Settings → Battery**, set the power-adapter energy mode to
   **High Power**.
4. Allow the machine to become idle before collecting preflight information.
5. Record the power source, battery state, load, and memory pressure:

```bash
pmset -g batt
uptime
top -l 1 -n 0 | head -n 10
memory_pressure
```

For the closest replication of this particular run, retain the configuration
order shown below. For a cleaner future baseline, begin with a charged battery,
let the computer cool, and record ambient and system temperature if suitable
instrumentation is available.

### Benchmark invocation

Run the following in `zsh` from the repository root:

```bash
mkdir -p raw

for spec in 128:128 128:256 256:128 256:256 512:128; do
  prompt_tokens=${spec%%:*}
  generation_tokens=${spec##*:}

  uv run --locked python -m mlx_lm.benchmark \
    --model "$MODEL_DIR" \
    --prompt-tokens "$prompt_tokens" \
    --generation-tokens "$generation_tokens" \
    --batch-size 1 \
    --num-trials 5 \
    --prefill-step-size 2048 \
    --delay 1 \
    2>&1 | tee "raw/p${prompt_tokens}_g${generation_tokens}.log"
done
```

The measured matrix, in execution order, was:

| Order | Prompt tokens | Generated tokens | Batch size |
| ---: | ---: | ---: | ---: |
| 1 | 128 | 128 | 1 |
| 2 | 128 | 256 | 1 |
| 3 | 256 | 128 | 1 |
| 4 | 256 | 256 | 1 |
| 5 | 512 | 128 | 1 |

Each invocation loads the model in a fresh process. MLX-LM then performs one
unmeasured warmup followed by five measured trials. The one-second delay occurs
before each measured trial.

### What MLX-LM measures

In MLX-LM 0.31.3, `mlx_lm.benchmark` performs the following operations:

1. Seeds the MLX random-number generator with `0`.
2. Loads the model and tokenizer before timing begins.
3. Creates random token IDs with the requested prompt length and vocabulary
   size.
4. Disables EOS termination so every trial generates the requested number of
   tokens.
5. Runs one complete, unmeasured warmup.
6. Calls `stream_generate` for each measured batch-one trial.
7. Reports prompt tokens/second, generation tokens/second, and MLX peak memory.

An outer `time.perf_counter()` records total trial duration. Total duration
includes the complete prefill and generation call but excludes model loading,
random-prompt construction, and warmup.

Within a configuration, the same generated prompt is reused for the warmup and
all five measured trials. A new process resets the seed for the next
configuration.

### Statistical treatment

For each configuration and metric, the report calculates:

- arithmetic mean;
- median;
- sample standard deviation using `n - 1`;
- coefficient of variation: `100 × standard deviation / mean`; and
- minimum and maximum, retained in the JSON analysis record where applicable.

No trial was discarded. Medians are the headline values because prompt
throughput included visible outliers. Five trials are sufficient to expose
gross instability, but not sufficient for precise tail-percentile estimates.

## Results

### Generation throughput and memory

| Prompt | Generate | Mean generation tok/s | Median generation tok/s | CV | Peak memory |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 128 | 128 | 59.840 | 59.971 | 0.93% | 4.923 GB |
| 128 | 256 | 59.366 | 59.393 | 0.50% | 4.923 GB |
| 256 | 128 | 59.536 | 59.593 | 0.58% | 5.064 GB |
| 256 | 256 | 58.657 | 59.089 | 1.29% | 5.064 GB |
| 512 | 128 | 57.439 | 57.363 | 1.05% | 5.217 GB |

### Prompt throughput and total duration

| Prompt | Generate | Mean prompt tok/s | Median prompt tok/s | Prompt CV | Median total time |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 128 | 128 | 897.002 | 950.720 | 10.14% | 2.396 s |
| 128 | 256 | 939.098 | 960.152 | 5.25% | 4.529 s |
| 256 | 128 | 1147.082 | 1254.467 | 12.97% | 2.465 s |
| 256 | 256 | 1034.719 | 972.618 | 19.62% | 4.721 s |
| 512 | 128 | 1248.470 | 1226.206 | 30.56% | 2.747 s |

## Interpretation

The strongest result is stable batch-one decode throughput near 60
tokens/second. Extending generation from 128 to 256 tokens at a fixed 128-token
prompt changed median throughput from 59.971 to 59.393 tokens/second, less than
1%. This suggests the generation measurement is long enough to produce a useful
steady-state result.

Median generation throughput declined to 57.363 tokens/second in the final
512-prompt configuration. The fixed execution order and ongoing battery charging
make it impossible to determine whether the difference came from prompt length,
thermal accumulation, charging load, or a combination of those factors.

Prompt throughput is not yet a dependable comparative baseline. Its high and
non-monotonic variation indicates that more warmups, more trials, randomized or
counterbalanced execution order, and thermal telemetry would improve the next
run. No values were removed as outliers in this report.

MLX peak memory grew by approximately 0.294 GB between the 128-token and
512-token prompt configurations, consistent with additional prompt/KV state.
This is MLX-reported peak allocated memory, not whole-process resident memory or
total system memory consumption.

## Reproduction checklist

A comparable run should preserve all of the following:

- the exact model commit, not only the Hugging Face repository name;
- the committed `uv.lock` environment;
- Apple Metal acceleration through MLX;
- batch size one;
- one warmup and five measured trials per configuration;
- `prefill-step-size=2048` and a one-second inter-trial delay;
- the listed configuration order, if replicating this run exactly;
- AC power and High Power adapter mode;
- no competing compute-heavy workloads; and
- raw, per-trial output with no discarded observations.

Record OS, MLX, MLX-LM, model revision, battery state, power mode, configuration
order, and any thermal or memory-pressure observations with every future result.
Restore the user's normal power mode after the benchmark.

## Known limitations and recommended follow-up

1. Repeat the matrix after charging the battery and cooling the machine.
2. Increase to at least ten measured trials for prompt-throughput comparisons.
3. Randomize or counterbalance configuration order to separate sequence length
   from thermal drift.
4. Add temperature, fan, package-power, and wall-power measurements where
   reliable tooling is available.
5. Add application-level tests for time to first token and natural-language
   prompts.
6. Automate log parsing and JSON creation so future reports are generated
   directly from raw output rather than transcribed.
